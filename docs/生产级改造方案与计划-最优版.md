> 版本：2026-07-12 综合自 `docs/改造路线图.md` 与对 `car-ecu-dev-agent/` 实际代码的逐文件核对。

## 2. 关键路径与并行关系

```
Phase 0 地基 ──┬─→ Phase 1 LLM真实化 ═╗
               │                        ║
               └─→ Phase 2 工具真实化 ═╝══→ Phase 3 记忆 ═→ Phase 4 评估收口 ═→ Phase 5 部署
                        └─(含 HITL 前置)╝        (Eval 已在 P1 起步)
```

- **关键路径**：`0 → 1 → 4`（地基 → LLM → 评估，Eval 必须紧跟 LLM 才有意义）
- **可并行加速点**：Phase 2 与 Phase 1 互不阻塞（都只依赖 Phase 0）
- **顺序硬约束**：HITL 审批必须早于"真工具上线"，否则编译烧录无人审即违规

## 3. 最优 MVP（2~3 周出真实生产力）

按「真实需求 → 真实生成 → 真实编译检查 → 真门禁」闭环，只投四步：

1. **Phase 0 配置加载 + trace_id 日志**（~2 天，零风险）
2. **Phase 1 编码 / 详设两阶段 `produce()` 真调 LLM 生成 C / 状态机**（~1 周，价值爆点）⭐
3. **Phase 2 接真实 `compiler` + `misra_checker`**（~1 周，门禁从假绿变真 gate）
4. **最小 Eval**（~3 天，与 2/3 并行建）

> 跑通后即与全 mock 本质不同：**真实需求 → 真实生成代码 → 真实编译 + 静态检查 → 门禁裁决**。

## 4. 不要做的事（风险提醒）

- ❌ 推翻 6 层 / V 模型骨架：契约正确，重写收益远小于风险
- ❌ 一次性接全部真实工具：会卡在 HIL / CANoe 重资源工具，先 compiler + misra 验证模式
- ❌ 丢掉 `scenario.py` 兜底：LLM 不可靠，模板回退是门禁确定性的安全网
- ❌ 只靠冒烟测试：它证明"能跑"，证明不了"生成质量"，Eval 必须同步建
- ❌ 把 Phase 0 误判为"已完成"而跳过：配置加载 / sys.path 清理 / pydantic / 错误 taxonomy 是后续所有阶段的硬前置
