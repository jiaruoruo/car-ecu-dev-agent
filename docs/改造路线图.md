# VDA Agent 改造路线图：从 POC 到可落地生产级

> 目标：把当前 Mock / 脚手架工程（`vda_agent`）改造为**真实可落地、具备生产力**的车载域控研发 Agent。
> 原则：**保留 6 层 + V 模型骨架契约 → 把"桩"换成真实实现 → 给骨架套上工程化外壳**。
> 用法：按 Phase 0 → 5 推进，每阶段有「TODO 清单」和「验收标准」，完成后勾掉并补记录。

---

## 0. 现状判断（改造前必读）

### 已经是生产级的部分（不要推翻重写）
- `Tool` / `ToolResult.data` 契约、以工具名为 key 的 `tool_results`（`core/tools.py`）
- `QualityGate` / `GateResult` 门禁框架（`core/feedback.py`）
- `MemorySystem` 四类记忆（工作/短期/长期/经验）（`core/memory.py`）
- `TraceLink` 追溯三态 `derives/satisfies/verifies`（`core/schemas.py` + `tools/traceability.py`）
- `STAGE_ORDER` + `REJECT_UPSTREAM` V 模型反向流（`core/orchestrator.py`）

### 真正的 POC 痕迹（改造焦点）
1. 所有 `produce()` 从 `stages/scenario.py` 取数，而非 LLM 生成工件；
2. 6 个工具全是确定性 stub（仅 `misra_checker` 有真实正则逻辑，其余固定返回成功）；
3. 记忆是本地文件 + 关键字检索，无向量/语义能力；
4. `config/settings.yaml` 只是参考文档，`factory.build_orchestrator` 并未真正加载它；
5. 仅 `tests/test_smoke.py` 一个冒烟测试，无组件单测 / 集成测试 / CI / 可观测性；
6. `HumanGate.auto_approve=true` 仅适合 CI demo，无真实人工介入闭环；
7. 无包管理（`sys.path.insert` 加 src）、无 Dockerfile / 服务接口、无增量重跑。

## Phase 1 · LLM 真实化（价值最高，核心突破）⭐

### TODO 清单
- [ ] 反转 `stages/scenario.py` 角色：从"唯一数据源"→"领域 few-shot / 检索上下文 + LLM 失败兜底模板"
- [ ] 改造 `produce()`（全部 7 阶段）：取上游黑板工件 + 召回记忆 → 拼 prompt → `LLMClient.generate(structured=True)` → 解析成 `content / items / trace_links`
- [ ] `core/llm_client.py` 升级：
  - 多 provider 抽象（Claude 写需求/设计，本地代码模型写 C，按需路由）
  - 强制结构化输出（JSON Schema / 函数调用），让 `items` / `trace_links` 由 LLM 直接产出
  - 埋点：token 用量、耗时、重试、降级（失败时回退 `scenario.py` 模板，保门禁确定性）
- [ ] 将当前"仅需求阶段用 Claude"的设定扩展到全部 7 个阶段

### 验收标准
- [ ] 给定一条**非防夹车窗**的真实需求，编码阶段能产出可编译的 C 骨架（不再是 `ANTIPINCH_C` 硬编码）
- [ ] LLM 失败时自动回退模板，流水线不中断、门禁仍确定
- [ ] `items` / `trace_links` 由 LLM 产出且通过 pydantic 校验（ID 格式一致、可双向追溯）
- [ ] `anthropic` 模式下 7 个阶段均调用真实模型，且 token / 耗时 metrics 可查

## Phase 2 · 工具真实化（让门禁"能信"）

### TODO 清单
- [ ] 优先接 `compiler`（AURIX tricore-gcc / S32 gcc 容器化调用）+ `misra_checker`（QAC / Polyspace）
- [ ] 每个真实工具实现同一 `Tool.run()` 契约，只改内部、不动返回字典字段；容器/子进程调用 + 超时 + `_CircuitBreaker`
- [ ] `autosar_arxml` → DaVinci / EB tresos（按需）
- [ ] `unit_test_runner` → Tessy / VectorCAST（按需）
- [ ] `hil_sil_runner` → CANoe / dSPACE HIL（视资源最后接）

### 验收标准
- [ ] 注入真实 MISRA 违规代码时，`misra_checker` 返回 `blocker_count > 0` → 编码门禁 FAIL → 触发 REPLAN 自修复
- [ ] 真实编译失败时，`compiler` 返回 `compiled=false` → 门禁 FAIL，而非 stub 的恒真
- [ ] 真实工具与 stub 切换仅靠配置，门禁代码 `tool_results.get("xxx")` 无需改动
- [ ] 工具调用超时 / 崩溃被 `_CircuitBreaker` 捕获并转为 `TransientError` 重试

## Phase 4 · 可观测性与评估（生产力的护城河）

### TODO 清单

### 验收标准

## Phase 5 · 安全 / 合规 / 部署（上车必备）

### TODO 清单
- [ ] `HumanGate`：生产接审批回调 / UI，`auto_approve` 仅限 CI；高风险工具（编译烧录、HIL）必须人工确认
- [ ] 密钥管理：API Key / 工具凭证走环境变量 / Vault，不落库
- [ ] 不可变审计链：`dump_artifacts` + 追溯矩阵落盘并签名，满足 ASPICE 证据留存
- [ ] `Dockerfile` + REST / CLI 服务接口，支持并发与异步
- [ ] **增量重跑**：基于 `TraceLink` 做变更影响分析，只重跑受影响下游阶段，而非每次全量 7 阶段
- [ ] 输入校验与权限：上游工件 / 用户请求进入流水线前做安全扫描与越权检查

### 验收标准
- [ ] 生产配置下，烧录 / HIL 类操作在无人审批时**被阻断**
- [ ] 任一次闭环的 7 份工件 + 追溯矩阵可审计、可签名、不可篡改
- [ ] `docker build` 出镜像，`docker run` 启动服务可接收请求并返回工件
- [ ] 修改需求文档后，仅需求下游（架构→…→集成）重跑，上游阶段命中缓存不重算

## MVP 最快出生产力路径（若只投一轮，约 2~3 周）

1. **Phase 0 配置加载 + 结构化日志**（~2 天，零风险）
2. **Phase 1 让编码 / 详设两阶段 `produce()` 真正调 LLM 生成 C / 状态机**（~1 周，价值爆点）
3. **Phase 2 接真实 `compiler` + `misra_checker`**（~1 周，门禁从假绿变真 gate）
4. **Phase 4 最小 eval**（~3 天，证明质量在提升）

> 跑通后获得本质不同于全 mock 的闭环：**真实需求 → 真实生成代码 → 真实编译 + 静态检查 → 门禁裁决**。

---

## 不要做的事（风险提醒）

- ❌ 推翻 6 层 / V 模型骨架：契约正确，重写收益远小于风险
- ❌ 一次性接全部 6 个真实工具：会卡在 HIL / CANoe 重资源工具，先 compiler + misra 验证模式
- ❌ 丢掉 `scenario.py` 兜底：LLM 不可靠，模板回退是门禁确定性的安全网
- ❌ 只靠 `test_smoke.py`：它证明"能跑"，证明不了"生成质量"，eval 必须同步建
